Wavetek PX2 Browser Extension

Proof of Concept and Remote Testing Proposal

Prepared for: Ash / Client TeamPrepared by: Development TeamVersion: 1.0Date: 23 September 2026

1. Executive Summary

This proposal describes the development and testing approach for a Chrome/Edge browser extension that will provide a Wavetek user interface for interacting with the PX2 device.

The PX2 already includes a browser-based WebUI. The proposed extension will not modify the PX2 hardware or firmware. It will communicate with the PX2 over the existing Ethernet connection and reproduce the approved requests currently used by the PX2 WebUI.

The work will begin with a focused Proof of Concept (POC). The POC will confirm that the extension can connect to the PX2, authenticate, read one basic setting, change one approved non-critical setting, and verify that the device accepted the change. Once proven, the solution can be expanded into the complete Wavetek interface.

2. Project Objective

The objective is to provide users with a Wavetek-branded Chrome/Edge extension through which supported PX2 settings can be viewed and updated.

Wavetek Chrome/Edge Extension → Ethernet Network → PX2 Device

The extension will act as the user-facing layer. The PX2 will remain responsible for applying and storing its settings.

3. Understanding of the PX2 WebUI

The PX2 WebUI is not a separate public website or desktop application. It is hosted inside the physical PX2 device and is opened from a computer on the same local network using the PX2 IP address.

Real integration therefore requires secure access to the London test network or to a computer connected to the device. The manual explains the WebUI features but does not provide its complete internal HTTP contract, so login and setting requests must be inspected on the real device.

4. Current Status

  • Manifest V3 Chrome/Edge extension shell
  • Wavetek-style POC interface and mock demonstration
  • Configurable device address and endpoints
  • Basic, form/session, and existing-session authentication options
  • Connection, permission, HTTP, and timeout feedback
  • Generic setting read/update workflow
  • No password persistence
Important: Current endpoint values are placeholders. Real PX2 discovery is required before hardware integration can be verified.

5. POC Scope

The POC will determine whether a Chrome/Edge extension can safely and reliably communicate with the PX2 and change an approved setting over Ethernet.

  1. Confirm PX2 WebUI connectivity.
  2. Identify the authentication method.
  3. Inspect WebUI read and save requests.
  4. Authenticate from the extension.
  5. Read one agreed setting, where supported.
  6. Change one safe, non-critical setting.
  7. Verify the new value in the original WebUI.
  8. Report errors clearly.
  9. Test in Chrome and Edge.
  10. Document findings and remaining work.

6. Recommended One-Time Remote Test Setup

To avoid requiring client assistance for every test, we recommend a one-time secure setup using a dedicated Windows computer in London.

Development Computer → Private VPN → London Test Computer → Ethernet → PX2
  • Tailscale or approved company VPN: private access without public exposure.
  • Dedicated London test computer: connected to the internet and PX2 network.
  • Optional remote desktop: AnyDesk, TeamViewer, or Chrome Remote Desktop for supervised troubleshooting.

7. Client-Side One-Time Requirements

  1. Provide a Windows test computer.
  2. Connect it to the PX2 through Ethernet.
  3. Confirm the PX2 WebUI opens in Chrome/Edge.
  4. Maintain a stable internet connection.
  5. Install and authorize the agreed private-access solution.
  6. Keep the computer powered on and awake during testing.
  7. Provide dedicated test credentials where possible.
  8. Confirm model and firmware version.
  9. Approve one non-critical setting for testing.
  10. Confirm applicable security policies.

8. Development and Testing Method

Phase 1 — Environment verification

Verify remote access, PX2 reachability, device/firmware details, network arrangement, and the approved setting.

Phase 2 — Request discovery

Inspect login, setting-read and setting-save traffic, including methods, paths, headers, cookies, content types, payloads, redirects, responses, and CSRF tokens.

Phase 3 — Extension integration

Implement the discovered endpoints, authentication/session handling, setting mapping, validation, and user-friendly errors without storing secrets in source control.

Phase 4 — Validation

Test authentication, read and update operations in Chrome and Edge, then verify the result through the original PX2 WebUI.

Phase 5 — Handover

Provide source code, setup guidance, technical integration notes, test results, and scope recommendations for the full interface.

9. POC Deliverables

  • Manifest V3 extension source code
  • Wavetek POC interface
  • Working PX2 connection and authentication
  • One setting-read flow where available
  • One verified setting-change flow
  • Error and status feedback
  • Installation instructions and technical notes
  • POC test results and limitations

10. Success Criteria

  1. The extension reaches the PX2.
  2. Authentication succeeds.
  3. One approved setting is read or its state obtained.
  4. The setting is changed through the extension.
  5. The change is verified in the original WebUI/device.
  6. Failures are reported clearly.
  7. The workflow is verified in Chrome and Edge.

11. Security Approach

  • Do not expose the PX2 administration interface publicly.
  • Use Tailscale, an approved VPN, or equivalent private access.
  • Restrict access to authorized accounts/devices.
  • Use dedicated test credentials where supported.
  • Never commit passwords, cookies, tokens, HAR files, or credentials.
  • Current POC credentials are not persisted.
  • Revoke remote access after testing.

12. Assumptions and Dependencies

  • A functioning PX2 is available in London.
  • A computer can connect to it over Ethernet.
  • The WebUI and valid credentials are available.
  • The client authorizes request inspection.
  • One safe setting is available for repeat testing.
  • The client can provide the one-time remote setup.

Proprietary authentication, firmware restrictions, browser incompatibilities, or corporate network policy may require additional investigation.

13. Outside the Initial POC

  • Implementation of every PX2 setting
  • Firmware or hardware modification
  • Public internet exposure
  • Extension-store publishing or production deployment
  • Enterprise identity integration
  • Fleet management and long-term support
  • Final production UI for every workflow

14. Work After a Successful POC

  4. Implement production-grade credential/session handling.
  5. Add recovery and compatibility support.
  6. Complete browser and firmware testing.
